# EXP13.3 — Identidade do vbmeta carregado vs backup local (read-only)

## Achados anteriores confirmados

EXP12 verificou todos os backups reais do Xiaomi Pad 6, slot `_b`. EXP13 e 13.1 confirmaram integridade estrutural de `vbmeta_b.img` e descritores.

A EXP13.2.1 **foi executada nos backups reais**, com os quatro SHA256 completos corretos:
- `boot`: `MISMATCH`, descritor 31.920.128 bytes vs fim de ramdisk em 32.204.801.
- `dtbo`: `MATCH`, descritor 692.224 bytes vs tabela em 688.455.
- `vendor_boot`: `MISMATCH`, descritor 20.697.088 bytes vs fim da DTB em 20.878.874.
- `RESULT=ONE_OR_MORE_MISMATCH`.

Isso demonstra divergência entre os descritores de hash de `vbmeta_b.img` e as imagens efetivamente salvas em backup, **mas não demonstra corrupção nem exige que o dispositivo falhe ao iniciar**.

O cabeçalho `vbmeta_b.img` declara `flags=3`, com `VERIFICATION_DISABLED`. Conforme [AOSP libavb, `avb_slot_verify.h`](https://android.googlesource.com/platform/external/avb/+/master/libavb/avb_slot_verify.h), se essa flag está aplicada no *top-level vbmeta*, seus descritores não são processados. A política de boot realmente aplicada ainda não está comprovada.

## Teste de correlação: SHA256 do blob top-level

A implementação AOSP [`avb_slot_verify_data_calculate_vbmeta_digest`](https://android.googlesource.com/platform/external/avb/+/master/libavb/avb_slot_verify.c) faz hash em sequência dos bytes de todas as imagens vbmeta carregadas. Cada item é o blob AVB, **não a capacidade integral da partição**.

Nos backups EXP13, o blob AVB principal tem `256 + 576 + 4352 = 5184` bytes, e a partição `vbmeta_b.img` possui `131072` bytes.

Um cálculo de `SHA256` dos primeiros 5184 bytes do backup, comparado ao valor de `ro.boot.vbmeta.digest`, pode fornecer indício de identidade da imagem carregada:
- Se for igual e o digest relatado for SHA256: correlação com o blob de vbmeta calculado localmente;
- Se diferir: não implica que `vbmeta_b` esteja corrompido, pois o digest relatado pode incluir `vbmeta_system` e outras imagens encadeadas, ou as propriedades podem não representar diretamente o valor carregado;
- Se vazio: resultado **inconclusivo**, em particular se verificação estiver desativada.

É uma comparação de **identidade**, não uma validação de assinatura, chave confiável, estado real de desbloqueio, rollback ou bootabilidade.

## Procedimento manual read-only

No PowerShell do Windows:

```powershell
$path = "C:\platform-tools\pipa_backup\vbmeta_b.img"
$actual = (Get-FileHash -LiteralPath $path -Algorithm SHA256).Hash.ToLowerInvariant()
$expected = "86d703c2ea2f73a55aa86374329bd89ffd975c0e95e33645a156cfdc343889ff"
if ($actual -ne $expected) { throw "REJECT: original vbmeta_b.img SHA-256 changed" }
$b = [IO.File]::ReadAllBytes($path)
if ($b.Length -ne 131072) { throw "REJECT: original vbmeta partition size changed" }
$sha = [Security.Cryptography.SHA256]::Create()
try { $blob = ([BitConverter]::ToString($sha.ComputeHash($b,0,5184))).Replace("-","").ToLowerInvariant() }
finally { $sha.Dispose() }
Write-Output "VBMETA_BLOB_SHA256=$blob"
Write-Output "ANDROID_VBMETA_DIGEST=$(C:\platform-tools\adb.exe shell getprop ro.boot.vbmeta.digest)"
Write-Output "ANDROID_VBMETA_HASH_ALG=$(C:\platform-tools\adb.exe shell getprop ro.boot.vbmeta.hash_alg)"
Write-Output "ANDROID_VBMETA_SIZE=$(C:\platform-tools\adb.exe shell getprop ro.boot.vbmeta.size)"
```

Saída de `getprop` pode estar vazia; não significa erro do comando, assinatura inválida nem falha do backup.

**`FLASH_READY=false`**. O usuário informou explicitamente que o bootloader do tablet está desbloqueado, apesar de os `getprop` anteriores dizerem `locked/green`. Não contrariar essa confirmação sem evidência independente. Não modificar `vbmeta`, boot ou estado de desbloqueio.
