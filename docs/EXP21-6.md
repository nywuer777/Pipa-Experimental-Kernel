## EXP21.6 — Homologação em dispositivo real (18/10/2026)

O usuário executou a EXP21.6 via ADB em Android normal, com slot ativo `_b`, consultando `id -Z` e `ls -lL` de quatro partições em cada slot. Resultado:

```text
ro.boot.slot_suffix: _b
id -Z: u:r:shell:s0
brw------- root root 8,76     boot_a
brw------- root root 259,40   boot_b
brw------- root root 259,21   dtbo_a
brw------- root root 259,46   dtbo_b
brw------- root root 259,20   vbmeta_a
brw------- root root 259,45   vbmeta_b
brw------- root root 259,28   vendor_boot_a
brw------- root root 259,52   vendor_boot_b
```

**Veredicto:** `EXP21.6_BLOCK_NODE_METADATA=PASS_REAL`; todos os oito nós de bloco têm modo Unix `0600`, proprietário `root:root`, e o shell ADB observado está em `u:r:shell:s0` e `uid=2000(shell)` segundo EXP21.5. Portanto, o shell não tem direito Unix de abertura de leitura desses nós; mecanismos de segurança adicionais SELinux também podem restringir acesso. A leitura de bytes **não foi tentada**. O modo `brw-------` é uma configuração de permissões, não uma falha nas partições; não inferir bootabilidade nem integridade de `_a`.

**Portão EXP21.7:** checar **somente a identidade do processo privilegiado** e com aprovação explícita no gerenciador de root, por exemplo `adb shell "su -c id"`, caso o usuário deseje prosseguir. Tal operação executa apenas `id`, **não acessa partições**, não eleva permanentemente o ADB, não altera SELinux, mas pode apresentar autorização interativa (KernelSU/Superuser) e o usuário deve poder recusá-la. A presença de `/system/bin/su` não garante autorização ou uid 0. Não executar automaticamente nem solicitar leitura de dados brutos até comprovar que existe acesso autorizado, e planejar hash somente leitura em ciclo separado. Se não houver autorização, parar esta linha de investigação em metadata-only, sem instalar utilitários ou manipular KernelSU.

# EXP21.6 — Inspeção de permissões dos nós A/B (somente metadados)

**Data:** 18/10/2026 | **Ponto de partida:** EXP21.5 `PASS_REAL`. O Android opera no slot `_b`, com ADB `uid=2000(shell)` e SELinux `u:r:shell:s0`. Os executáveis `su`, `sha256sum` e `blockdev` existem no PATH, mas root e leitura de bloco permanecem não comprovados.

## Objetivo da etapa

Distinguir os *links simbólicos* A/B já observados na EXP21.3 dos nós de dispositivo que eles apontam, vendo permissões Unix, usuário/grupo proprietário e eventualmente contexto SELinux, sem ler um único byte do conteúdo da partição. A execução permanece `uid=2000(shell)`; não tentar root, nem modificar slots ou a imagem candidata.

## Windows PowerShell — consultas somente leitura

```powershell
$adb = "C:\platform-tools\adb.exe"

& $adb devices -l
& $adb shell getprop ro.product.device
& $adb shell getprop ro.boot.slot_suffix
& $adb shell id
& $adb shell id -Z

& $adb shell ls -lL `
  /dev/block/by-name/boot_a `
  /dev/block/by-name/boot_b `
  /dev/block/by-name/vendor_boot_a `
  /dev/block/by-name/vendor_boot_b `
  /dev/block/by-name/dtbo_a `
  /dev/block/by-name/dtbo_b `
  /dev/block/by-name/vbmeta_a `
  /dev/block/by-name/vbmeta_b
```

Se o `ls -lL` ou `id -Z` não forem suportados ou retornarem `Permission denied`, registrar o erro; não contornar permissões nesta rodada. `ls -lL` segue o link apenas para consultar metadados do alvo. Não usa `dd`, `sha256sum` sobre nós de bloco, `blockdev --getsize64`, nem `su -c`.

## Interpretação e gates

- Um nó `brw------- root root` (exemplo hipotético) indica restrição Unix aparente para `shell`, mas a decisão efetiva pode incluir SELinux e mecanismos privilegiados. O exemplo não deve ser tomado como o resultado do tablet.
- `ls -lL` não comprova que o conteúdo seja íntegro, nem que o slot A é inicializável.
- Não executar `su -c id` automaticamente. Se for necessária uma futura auditoria de partição por root, só fazê-la mediante **autorização específica** de operação read-only, após avaliar riscos, permissões, aplicação KernelSU/Superuser e coleta de hashes sem extrair dados privados.
- Não tratar a partição `_a` como reserva até comprovar conteúdo e compatibilidade de firmware/sistema; ambos os slots terem `successful=yes` continua sendo apenas metadado administrativo.
- O candidato EXP06 offline passou nas EXP19/20, mas não foi instalado nem testado em boot.
